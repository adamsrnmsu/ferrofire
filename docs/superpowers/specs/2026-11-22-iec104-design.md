# IEC 60870-5-104 server and client in Rust (ww-vck)

Status: draft, 2026-11-22. Bead ww-vck (beads in ~/git/phenix-waterway-range).

Measured stock (bennu tag v2026.11.03) corrects this text where they differ, per the ledger's Ruling 4 and
`conformance/iec104/STOCK.md`; the corrected lines say so.

## Intent

IEC 104 is the one protocol stock `bennu-field-device` serves that ferrofire does not. A range that uses
`<iec60870-5-104-server>` (generated by the sceptre app for `iec60870-5-104` field devices) or `<iec60870-5-104-client>`
(fd-client and FEP hosts) cannot run ferrofire in bennu's place today. This work closes that gap. The aim is drop-in:
stock config in, stock behaviour on the wire out, judged against the stock device as the oracle, as Modbus and DNP3 were.

The first attempt was an external Python module on c104. It failed: c104 keeps one point per IOA, and stock serves an
output at the same IOA both in interrogation and as a command target (`modules/iec104/spike/NOTES.md`). The user then
chose a compiled Rust module, in process, like DNP3 (2026-11-21), and chose writing the protocol by hand over a crate
(2026-11-22).

## Goals

- `<iec60870-5-104-server>` as specified in field-device-spec.md 4.3: config keys, single and double point modes, STARTDT,
  general interrogation (QOI 20 only, all points including outputs, ordered by address), the periodic report every
  `rpoll-rate` s to the last opened connection, commands 45, 46 and 50 with stock's confirmations, and quirk Q11 (`subtype` required). Q7 ("the select bit
  is ignored") does not hold at the tag: stock refuses a select with a negative ACT_CON and writes nothing (Ruling 4, STOCK.md).
- `<iec60870-5-104-client>` as specified in the protocols plan, row 10:
  - `<iec60870-5-104-connection>` blocks, tcp only;
  - originator 3, CA 1;
  - STARTDT, then one GI at connect, then the server's periodic data;
  - decodes `M_ME_NC_1` and `M_DP_NA_1`. Q12 is replicated, so binaries never update from a `single` server; `--strict` also
    decodes `M_SP_NA_1`;
  - writes `C_DC_NA_1` and `C_SE_NC_1` by direct execute, select 0 (Ruling 4, STOCK.md "Client"; the tag's sample would select
    only with `sbo-enabled` true, not built: ww-3a4);
  - serves the stock `<command-interface>` (src/fd/cmdif.rs).
- A ferrofire `fep` mode for the 104 client, as for the Modbus and DNP3 clients (docs/field-device-clients.md, "`fep` mode";
  the user's choice, 2026-11-22). `<mode>` is `bennu` (default, stock behaviour above) or `fep`; anything else is a config error naming
  it.
  - **Poll:** `<scan-rate>` per connection (seconds, decimals allowed, default 1) sends a GI. 104 has no per-point read that stock
    answers: it answers type 102 with COT 44. The GI's data and every periodic or spontaneous ASDU feed the tags. Single, double and
    float types are all decoded: Q12 is a `bennu`-mode quirk only.
  - **`<status-tag>`:** true while the connection has a STARTDT session and its last GI got ACT_TERM.
  - **Writes down:** once per `<cycle-time>`, the output tags that changed locally go down as `C_SC_NA_1`, `C_DC_NA_1` (by the
    server's mode, learned from the GI's binary type) or `C_SE_NC_1`, as direct execute.
  - **Echo rule, grace after a write, NaN never sent, away-device backoff (1, 2, 4 ... s up to 60 s), newest-value-on-return:** as
    the shared rules in `src/fd/proto/client.rs` and that doc section. A command is answered when ACT_CON arrives; a negative
    ACT_CON means refused, not repeated.
  - In `bennu` mode `<scan-rate>` and `<status-tag>` are a WARN, an error under `--strict`, as for the other clients.
  - Tests: unit tests of the poll, status and write-down rules; a ferrofire 104 FEP against ferrofire's own 104 server and against
    stock's, in `tests/` like the existing FEP tests. The FEP is ferrofire-only, so there is no stock golden for it.
  - docs/field-device-clients.md gains the 104 client: title, table rows, and a `fep` bullet.
- Stock sample configs load with no edits: `conformance/stock/iec104-server.xml` and bennu's sample client.
- Conformance against stock, in the existing harness:
  - `conformance/iec104`: our server against stock's, with the same config and probe. Byte-equal transcript but for listed
    divergences; tshark (`iec60870_104` dissector) decodes with no malformed packets. Zeek is skipped: the testpeers
    image has no IEC 104 parser (ICSNPP ships none). Adding one is out of scope (my call, from the builder check).
  - Stock's 104 client against our server.
  - `conformance/iec104-client`: our client against stock's 104 server, transcript equal to stock client against stock server.
- Event logging as stock does it for this module (`<event-logging>`).
- The six gates pass (`make fmt-check lint test crap dry deny`).

## Non-goals

- TLS (IEC 62351), redundancy groups, more than one common address, file transfer, time sync, counter interrogation, any
  type id stock does not handle. For those, answer as stock answers (to be recorded); do not implement them.
- `fep` features beyond the Modbus and DNP3 FEPs' rule set.
- A reusable 104 crate for others. The code lives in `src/fd/proto/iec104/` like `dnp3/`.
- Benchmarks of 104 performance in the comparison (a later bead if wanted).

## Anti-goals

- Any GPL-3.0 dependency (lib60870 and its FFI wrappers). ferrofire is MIT.
- A new protocol crate dependency. The user picked hand-written, for full control of stock's quirks.
- Wire behaviour that differs from stock and is not listed as a divergence with its reason.
- Changing behaviour of the other protocols or the external-module boundary.

## Approaches considered

1. **Write it by hand, like DNP3 (chosen).** No dependency, MIT, full control of stock's quirks (outputs in GI and commandable at
   one IOA, the last-connection periodic sender, Q12). Reuses the DNP3 module's shape: frame layer, state machine without I/O,
   a thin tokio shell. Most code, but 104 is smaller than DNP3 (DNP3 here is about 5,300 lines).
2. `iec104` crate 0.6.0 (MIT, "API still evolving"). Less code; risks the same one-point-per-IOA model c104 had, and churn.
3. `fegrid-iec60870-*` 0.1.0 (sans-IO, under 100 downloads). Too young to build on.

## Design

### Layout

`src/fd/proto/iec104/` behind the existing empty Cargo feature `proto-iec104`:

- `apci.rs`:
  - APDU framing (`68 len`, 253-byte maximum);
  - I, S and U frames, with send and receive sequence numbers;
  - the k/w windows and the t1, t2 and t3 timers.
  - Sans-IO: bytes in, frames and actions out.
- `asdu.rs`:
  - the ASDU header (type, VSQ, COT, originator, CA 2 bytes, IOA 3 bytes LE);
  - the types used: 1, 3, 13, 31, 45, 46, 50, 100, with SIQ, DIQ, QDS and CP56Time2a;
  - encode and decode, with an error for any other type that keeps the raw type id so the server can answer it.
- `server.rs`: the slave state machine without I/O: STARTDT/STOPDT/TESTFR, GI, commands, the periodic report built from a store
  snapshot, and splitting at the maximum ASDU payload.
- `client.rs`: the master state machine without I/O, plus the cmdif points.
- `mod.rs`:
  - config parsing for both elements, with the stock key names and errors;
  - the REGISTRY entries;
  - the tokio shell: listener or connector, the `rpoll-rate` tick, the event log;
  - writes into the store's updated-tag queues as the other servers do.

### Behaviour that is not yet pinned (resolved by measurement first)

Spec 4.3 marks these UNVERIFIED. They are settled by recording stock before any code is written, with the existing
`conformance/stock/probe_104.py`, the wider `modules/iec104/spike/probe_ext.py`, and new probes where needed. The spike's stock
transcripts in `modules/iec104/spike/out/` already cover part of this.

- confirmations per command type: spec 4.3 gives 45 and 50 only an echo (COT 7) and 46 ACT_CON + ACT_TERM, but the spike's
  `out/stock-double.txt` shows ACT_CON then ACT_TERM for 45 as well; the goldens decide;
- answers to type ids 101, 102, 103, 105 and 107 (the spike saw `6c`, COT 44, for 101-103), and to a command at an unknown IOA
  (`47`, negative ACT_CON);
- TESTFR handling, and t1, t2, t3, k and w as seen on the wire (how long stock waits before an S-frame, when it closes on a missing
  ack);
- several clients at once: what a second connection gets, and the last-opened periodic rule;
- double-point periodic `M_DP_TB_1` per point with COT 3, and its timestamps (masked in transcripts);
- what the client does on a lost connection: whether it reconnects and when; and what `ERR` the cmdif gives with no server.
  Measured (STOCK.md "Client"): it never reconnects, after a lost connection or a failed first connect, and the cmdif gives no
  `ERR` for it: reads answer the last values and writes are ACKed.

Where stock's value comes from lib60870 defaults that cannot be observed, use the IEC 60870-5-104 standard values (k 12, w 8,
t1 15 s, t2 10 s, t3 20 s) and say so in the conformance README.

### Config and loading

- Element names, keys and errors follow stock's DataHandler: endpoint `tcp://` only, `rpoll-rate` required, `subtype` required
  (Q11), addresses uint16.
- A wrong or missing key is a clear error naming the key, as the DNP3 module does.
- Tags: the server maps existing `<tags>` like the other servers. The client declares its points' tags at parse through
  `client::point_tag`, like the other compiled clients.
- Once compiled, the REGISTRY wins over any manifest for these tags (Ruling 9 of the external-modules work).
- Update the tests that assumed no compiled 104: `registry_wins_over_a_manifest` (`src/fd/proto/mod.rs`) and the manifest
  tests' global DIR. Both assume no compiled 104. `registry_wins_over_a_manifest` asserts
  `!compiled("iec60870-5-104-server")` and must flip to assert the compiled module wins. The manifest tests set a
  process-global modules DIR, so a 104 feature-error test must not depend on whether a manifest is visible.

### Testing

- Unit tests per layer:
  - APCI sequence numbers and wrap;
  - window and timer actions with a fake clock;
  - every ASDU type round-tripped, against the byte strings in spec 4.3 and the stock transcripts;
  - GI order and contents in both modes;
  - command echoes;
  - client decode with and without `--strict`.
- A no-panic test feeding random and truncated byte streams through the APCI and ASDU decoders (seeded, no new dependency).
  Invariant: no panic, bounded memory, the connection closed on a violation.
- Conformance directories as above, with stock goldens recorded first (`run-stock.sh 104` plus new probes). Divergences go in
  `conformance/README.md` with whose they are and why.
