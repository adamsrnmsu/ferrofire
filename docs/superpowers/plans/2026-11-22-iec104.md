# IEC 60870-5-104 Server and Client Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a compiled, hand-written IEC 104 server and client (bennu and fep modes) in ferrofire, drop-in for stock configs and judged on
the wire against stock bennu-field-device.

**Architecture:** `src/fd/proto/iec104/`, shaped like `dnp3/`:
- Bottom layers without I/O: `apci` (frames, sequence numbers, windows, timers) and `asdu` (the types stock uses).
- State machines without I/O: `server` (the slave) and `client` (the master).
- A tokio shell in `mod.rs`, with the config parsing and the REGISTRY lines behind the existing feature `proto-iec104`.

Stock facts the spec marks UNVERIFIED are recorded from the stock device first (Task 0), and every later task codes to that record.

**Tech Stack:** Rust (tokio, roxmltree, the crates already in Cargo.toml), the conformance harness (`conformance/run.sh`,
ferrofire-testpeers image, tshark), the stock oracle image `ffc-stock-2026.11.03:22.04`.

**Spec:** `docs/superpowers/specs/2026-11-22-iec104-design.md`. It binds; field-device-spec.md 4.3 and the protocols plan, row 10,
are its sources.

## Global Constraints

- **Licence:** ferrofire is MIT. No GPL-3.0 dependency (lib60870, lib60870-sys). No new crate dependency of any kind for the protocol.
- **Stock sources:** `~/git/sceptre-bennu` is READ ONLY; cite its lines, never vendor them.
- **Drop-in configs:** `conformance/stock/iec104-server.xml` and `~/git/sceptre-bennu/data/configs/ep/iec60870-5-104-client.xml`
  (copied to `conformance/stock/client-iec104.xml`) load with no edits.
- **Wire behaviour:** any difference from stock is listed in `conformance/README.md` with whose it is and why. Otherwise it is a bug.
- **Stock config rules:** endpoint `tcp://` only; `rpoll-rate` and `subtype` required (Q11); `subtype` containing `double` means
  double-point mode; CA fixed at 1; IOA 3 bytes LE from a uint16 `address`; originator 0 (server) and 3 (client); the select bit is
  ignored (Q7).
- **Q12:** the bennu-mode client decodes only `M_ME_NC_1` and `M_DP_NA_1`; `--strict` and `fep` mode also decode `M_SP_NA_1`.
- **`<mode>`:** `bennu` (default) or `fep`, through `proto::client::mode`. `<scan-rate>` and `<status-tag>` go through
  `proto::client::fep_keys`. The FEP rules are those of docs/field-device-clients.md "`fep` mode" and `proto/client.rs` (`Out`,
  `Echo`, `input_polled`, `TagPoints`).
- **APCI values stock cannot show:** use the IEC 60870-5-104 standard values, k 12, w 8, t1 15 s, t2 10 s, t3 20 s.
- **Gates:** `make fmt-check lint test crap dry deny` all pass (CRAP < 10, dry < 0.8).

  - Run crap under `timeout 1500`.

## Review Focus

1. **A master that sends nothing, or I-frames before STARTDT:** the server must not crash or leak; it answers as stock does (Task 0
   records it). Test in Task 3.
2. **A master that never acknowledges:** once k I-frames are unacknowledged, the server stops sending and closes after t1, as the
   standard (and stock, per Task 0) does. Nothing is queued without bound. Test in Task 1.
3. **Two masters at once:** both get STARTDT and GI answers; periodic data goes to the last opened connection only. When that one
   closes, it goes to the one still open (per Task 0). Test in Task 4.
4. **One address used by a binary and an analog point, or a float tag holding NaN or inf:** GI and periodic carry both points, and the
   float is sent as its float32 bits with no panic. Test in Task 3.
5. **Client against an absent or vanishing server:** the reconnect timing and the cmdif `ERR` texts are stock's (Task 0). The scan
   cycle is never blocked. Tests in Task 5 (bennu) and Task 6 (fep).

### Task 6: The 104 client's `fep` mode

**Files:**
- Modify: `src/fd/proto/iec104/client.rs`, `src/fd/proto/iec104/mod.rs`
- Test: `tests/iec104_fep.rs` (style of `tests/fd_fep.rs`)
- Modify: `docs/field-device-clients.md` (title, the `<mode>` / `<scan-rate>` / `<status-tag>` table rows, a 104 bullet under

**Interfaces:**
- Consumes: Task 5's `Master` and `Conn`, and `proto::client::{Out, Echo, input_polled, TagPoints, cycle}`.
- Behaviour, from spec Goals "fep mode":
  - one GI every `<scan-rate>`;
  - GI data and periodic or spontaneous data feed the tags: inputs through `input_polled`, outputs through `Out::polled`;
  - every type is decoded;
  - `<status-tag>` is true while STARTDT is up and the last GI got ACT_TERM;
  - every `cycle(node)`, `Out::due` changes go down as `C_SC_NA_1` or `C_DC_NA_1` (the server's mode, learned from the GI's binary
    type id; before the first GI, `C_SC_NA_1`) or `C_SE_NC_1`, direct execute;
  - ACT_CON positive calls `sent_ok`, negative calls `sent_failed` and the command is not repeated;
  - NaN is never sent (a WARN);
  - backoff 1, 2, 4 ... s up to 60 s;
  - the newest value of each changed tag is sent on return, before the GI;
  - the cmdif is `TagPoints`.
